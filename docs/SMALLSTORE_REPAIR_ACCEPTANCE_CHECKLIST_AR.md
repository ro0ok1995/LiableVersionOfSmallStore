# قائمة اختبار قبول إصلاحات SmallStore

> هذه القائمة مخصصة للاختبار اليدوي على نسخة تجريبية/قاعدة بيانات منسوخة. لا تستخدم قاعدة بيانات المتجر الوحيدة. لا تعتبر أي بند ناجحاً إلا بعد تسجيل النتيجة الفعلية وإرفاق صورة/سجل عند الحاجة.

## بيانات الاختبار المقترحة
- المورد A والمورد B.
- المنتج P واحد مرتبط بالموردين.
- سعر شراء P من A = 20 شيكل، ومن B = 15 شيكل.
- فاتورة A-1: 5 وحدات بسعر 20.
- فاتورة B-1: 8 وحدات بسعر 15.
- فاتورة B-2: 4 وحدات بسعر 17.
- إجمالي الكمية قبل البيع: 17 وحدة.
- اجعل سعر البيع ثابتاً، مثلاً 28 شيكل، ولا تغيّره أثناء الاختبارات.

سجل لكل بند: [ ] ناجح [ ] فاشل [ ] لم يُختبر، مع رقم الإصدار والجهاز ولقطة شاشة/سجل.

## A. أرقام فواتير الشراء
- [ ] إنشاء أول فاتورة شراء دون إدخال رقم يدوي؛ يتولد رقم فريد.
- [ ] إنشاء فاتورة ثانية للمورد نفسه؛ لا يتكرر الرقم.
- [ ] إنشاء فاتورة ثالثة لمورد مختلف؛ لا يتكرر الرقم.
- [ ] إغلاق التطبيق وإعادة فتحه ثم إنشاء فاتورة؛ يستمر التسلسل دون إعادة استخدام رقم.
- [ ] وجود أرقام تاريخية بصيغة `PUR-FIX-*` لا يعيد التسلسل إلى `PUR-000001`.
- [ ] إدخال رقم يدوي مكرر يُرفض برسالة مفهومة ولا يُحفظ أي جزء من الفاتورة.
- [ ] محاولة إنشاء فاتورتين متزامنتين/متتاليتين لا تنتج رقماً مكرراً.
- [ ] عند فشل حفظ بند أو حركة مالية، لا تبقى فاتورة يتيمة أو حركة مخزون/مال جزئية.

## B. سلة مشتريات المورد
- [ ] إضافة منتج P إلى ارتباط المورد A ثم إضافته للسلة.
- [ ] حذف ارتباط P بالمورد A قبل تأكيد الفاتورة؛ يُزال P من السلة مباشرة.
- [ ] تبقى المنتجات الأخرى في السلة كما هي.
- [ ] لا يمكن تأكيد فاتورة تحتوي منتجاً لم يعد مرتبطاً بالمورد.
- [ ] إعادة فتح شاشة المورد لا تعيد العنصر المحذوف من حالة السلة المحفوظة.
- [ ] ارتباط P بالمورد B لا يتأثر بحذف ارتباطه بالمورد A.

## C. عكس فاتورة شراء بالكامل
- [ ] شراء 5 وحدات ثم عكس الفاتورة قبل بيع أي وحدة؛ تنجح العملية إذا كانت بقية الشروط تسمح.
- [ ] شراء 5 وحدات وبيع الخمس ثم محاولة العكس؛ يُمنع العكس.
- [ ] تظهر نافذة توضح سبب المنع والكمية المتاحة/المستهلكة إن كانت البيانات متاحة.
- [ ] بعد المنع، تبقى الفاتورة والرصيد والمخزون والحركات كما كانت قبل المحاولة.
- [ ] فاتورة لها مرتجع مشتريات نشط لا تُعكس بطريقة تؤدي إلى احتساب الأثر مرتين.

## D. مرتجع مشتريات جزئي
- [ ] فتح إجراء المرتجع من نشاط المورد/الفاتورة الأصلية.
- [ ] إرجاع 3 وحدات من فاتورة 8 وحدات؛ تنجح العملية.
- [ ] ينخفض مخزون المنتج 3 وحدات فقط.
- [ ] ينخفض مستحق المورد أو يُسجل الاسترداد النقدي وفق التوزيع الذي اختاره المستخدم.
- [ ] يظهر المرتجع في نشاطات الموردين كـ«مرتجع مشتريات»، وليس كعكس فاتورة.
- [ ] إرجاع وحدات إضافية لاحقاً مسموح حتى حد الكمية المتبقية القابلة للإرجاع.
- [ ] محاولة إرجاع كمية أكبر من المتبقي تُرفض دون تغيير أي رصيد.
- [ ] المرتجع النقدي يسجل في الحساب المالي المختار مرة واحدة فقط.
- [ ] يظهر سبب المرتجع وملاحظاته إن كانا مدخلين.

## E. مرتجع المبيعات والنشاطات
- [ ] بيع وحدة من P للعميل.
- [ ] إرجاع الوحدة مع رد نقدي فوري بقيمة مختلفة مسموح بها وفق قواعد التطبيق (مثال 20 شيكل).
- [ ] يظهر مرتجع المبيعات في نشاطات المتجر ضمن الفترة الصحيحة.
- [ ] لا يظهر المرتجع مرتين نتيجة وجود سجل مرتجع وسجل معاملة.
- [ ] يعرض النشاط اسم المنتج والعميل/المرجع والمبلغ المصروف ووسيلة الدفع وسبب المرتجع.
- [ ] ينخفض صافي المبيعات/الذمم وفق نوع البيع والرد، ولا يتغير سجل البيع الأصلي.
- [ ] تزيد كمية المخزون المرتجعة مرة واحدة فقط.

## F. اتجاه وتصنيف الأسهم
- [ ] مرتجع المشتريات يظهر كخروج مخزون باتجاه المورد في وصف/رمز المخزون.
- [ ] أثره المالي يوضح تخفيض مستحق المورد أو استرداد النقدية، ولا يخلط بين الاتجاهين.
- [ ] عكس فاتورة الشراء يظل تصنيفاً مستقلاً عن مرتجع المشتريات الجزئي.
- [ ] مرتجع المبيعات يظهر كدخول مخزون من العميل، مع أثر مالي واضح للرد.
- [ ] ألوان الحركات متسقة مع بقية نشاطات العملاء والموردين، ولا تعتمد على إشارة المبلغ وحدها لتحديد نوع العملية.

## G. دفعات المخزون وترتيب الأولوية
- [ ] شراء 5 وحدات من A بسعر 20؛ تتكون دفعة مستقلة مرتبطة بالفاتورة والمورد والتكلفة.
- [ ] شراء 8 وحدات من B بسعر 15؛ تتكون دفعة ثانية مستقلة.
- [ ] شراء 4 وحدات أخرى من B بسعر 17؛ تتكون دفعة ثالثة مستقلة رغم تطابق المورد والمنتج.
- [ ] نافذة مخزون P تعرض كل دفعة منفصلة: المورد، الفاتورة، التاريخ، تكلفة الوحدة، الكمية الأصلية والمتبقية.
- [ ] تغيير ترتيب الدفعات وحفظه.
- [ ] إغلاق التطبيق وإعادة فتحه؛ يبقى الترتيب محفوظاً.
- [ ] عند البيع، تُستهلك الدفعة ذات الأولوية الأعلى أولاً.
- [ ] إذا كانت كمية البيع أكبر من رصيد الدفعة الأولى، ينتقل النظام تلقائياً للدفعة التالية.
- [ ] عند نفاد دفعة، لا يحاول النظام استهلاكها مرة أخرى.
- [ ] تغيير الأولوية بعد بيع سابق لا يغير مصدر أو تكلفة المبيعات التاريخية.
- [ ] إضافة فاتورة شراء جديدة تنشئ دفعة جديدة ولا تمحو أو تدمج الدفعات القديمة.
- [ ] لا يضطر الكاشير لاختيار دفعة أو مورد أثناء عملية البيع.
- [ ] سعر البيع للعميل يبقى مستقلاً عن تكلفة الدفعة.

## H. التكلفة والمرتجعات المرتبطة بالدفعات
- [ ] بيع كمية من دفعة واحدة يحفظ مصدرها وتكلفة الوحدة التاريخية.
- [ ] بيع كمية تتجاوز رصيد الدفعة الأولى يحفظ توزيع الكمية والتكلفة على الدفعات المستخدمة.
- [ ] تقرير تكلفة البضاعة المباعة يساوي مجموع (كمية كل دفعة مستهلكة × تكلفتها التاريخية).
- [ ] مرتجع مبيعات يعيد الكمية إلى دفعتها الأصلية متى كان الربط معروفاً.
- [ ] إعادة البيع بعد المرتجع تتبع قواعد الأولوية الحالية دون تعديل السجل التاريخي.
- [ ] إذا كان مصدر كمية قديمة مجهولاً، تُحفظ كرصيد افتتاحي/دفعة مجهولة المصدر ولا يُخترع لها مورد أو سعر.
- [ ] المرتجع لا يضيف كمية إلى دفعة خاطئة ولا يضاعف تكلفة المخزون.

## I. ترحيل قاعدة البيانات وحماية البيانات
- [ ] أخذ نسخة احتياطية قبل الترقية.
- [ ] ترقية قاعدة بيانات فعلية من الإصدار 26 إلى الإصدار الجديد دون حذف/إعادة إنشاء الجداول.
- [ ] عدد المنتجات والعملاء والموردين والفواتير والمبيعات والمرتجعات قبل وبعد الترقية متطابق.
- [ ] إجمالي كمية المخزون لكل منتج قبل وبعد الترقية متطابق تماماً.
- [ ] أرصدة الموردين والعملاء والحسابات المالية قبل وبعد الترقية متطابقة.
- [ ] بيانات التكلفة التاريخية المعروفة تبقى كما هي.
- [ ] الكميات القديمة غير القابلة للإسناد إلى فاتورة تُسجل كمخزون افتتاحي غير محدد المصدر، ولا تختفي.
- [ ] استيراد JSON/استعادة نسخة احتياطية قديمة لا يؤدي إلى دفعات مكررة أو أرقام فواتير مكررة.
- [ ] اختبار التراجع/استعادة النسخة الاحتياطية على جهاز تجريبي.

## J. الأداء والاستقرار
- [ ] فتح شاشة المنتجات والتنقل بينها لا يسبب استعلام دفعات لكل إعادة رسم Compose.
- [ ] تفاصيل الدفعات تُحمّل عند فتح نافذة المخزون فقط.
- [ ] بيع كمية كبيرة موزعة على دفعات يتم داخل معاملة قاعدة بيانات ذرية.
- [ ] لا تظهر أرصدة سالبة للدفعات أو للمخزون.
- [ ] لا يتكرر خصم المخزون عند تدوير الشاشة أو إعادة المحاولة.
- [ ] لا يتكرر الأثر المالي عند إعادة إرسال العملية.
- [ ] لا يوجد Crash عند فتح نافذة المخزون أو ترتيب الدفعات أو البيع أو المرتجعات.
- [ ] نجاح `./gradlew test`.
- [ ] نجاح `./gradlew assembleDebug`.
- [ ] نجاح اختبارات Room Migration على قاعدة بيانات الإصدار 26.
- [ ] تثبيت APK على جهاز Android وتنفيذ السيناريوهات A إلى I عملياً.
